# Kimi Work 0.1.11 compatibility

## Scope

This candidate incorporates upstream through `28f9cbb3b26ccc3a7739c8e21ebee0cda3d929d4` (kimi-work 0.1.10), including the model-effort parser, desktop Work menu, device headers and unauthenticated menu retry. Membership renewal and the single monthly shared-pool meter are additions to that baseline. The interfaces are undocumented and can change.

The current live renewal test uses Apple-silicon macOS and official Kimi Desktop **3.2.17** (build 3.2.17.4). A fresh, user-completed login belongs to disposable profiles. The installed application and everyday Magpie/Kimi profiles are not the test credential source. A temporary application copy keeps the original `app.asar` byte-for-byte; its main-source SHA-256 is `6a37077974207f7b501add47d9756eaff8d41eb87347e05b11f59f7b2386c439`. Test-only launch instrumentation redirects profile paths and exposes the original AuthService and TokenStore methods for invocation/observation; no refresh response is substituted.

## RefreshToken request comparison

Endpoint: `POST https://auth.kimi.com/api/account.gateway.v1.AuthService/RefreshToken`. The official native request was observed at **2026-10-24 15:14:47 UTC**, HTTP **200**, producing changed access and refresh tokens. The full request-header names below come from Electron's send-headers event; private values were redacted in memory before recording.

| Header | Official desktop 3.2.17 | Plugin's explicit request |
| --- | --- | --- |
| `Authorization`, `Cookie` | Both absent | Both absent; regression asserted |
| `User-Agent` | Chromium UA containing `kimi-desktop/3.2.17 Chrome/150.0.7871.250 Electron/43.7.3` | Same captured macOS UA; OS portion follows platform |
| `x-msh-platform` | `mac` | `mac` on macOS, `windows` on Windows, `web` otherwise |
| `x-msh-version` | `3.2.17` | `3.2.17` for AuthService only |
| `R-Timezone` | `Asia/Singapore` | Runtime timezone (`Asia/Singapore` in this run) |

| `Connect-Protocol-Version` | `1` | `1` |
| `Content-Type` | `application/proto` | `application/json` |
| `x-msh-device-id`, `x-msh-session-id`, `x-msh-shield-data` | Present; values redacted | Omitted; no browser identity/signature copied |
| `X-Traffic-Id` | Absent before token import; present on the later signed-in renewal, value redacted | Omitted; no account identifier copied |
| `Sec-Fetch-Site`, `Sec-Fetch-Mode`, `Sec-Fetch-Dest` | `none`, `no-cors`, `empty` | Only `Sec-Fetch-Mode: cors`, generated by Node |

| `Accept` | Not explicitly present in the capture | `application/json` |

The request bodies use the same `RefreshTokenRequest.refresh_token` field. The original SDK selects protobuf by default and also implements Connect JSON with `useProtoFieldName: true` when its `KIMI_CAPTURE` option is set. The plugin uses that JSON representation, rather than adding a protobuf runtime. The official interceptor adds device/session/shield fields only when available; the plugin does not mint or reuse those browser-owned values. These are intentional differences, not a claim of byte-identical requests. The real plugin request at **15:21:07 UTC** was accepted with **200**, changed both tokens, and read `GetSubscriptionStats` with **200** at **15:21:08 UTC** without those optional fields.

Plugin transport-generated fields above were observed through Node's `undici:request:create` event on the **15:36:50 UTC** real renewal, in addition to the explicit fetch options. The observer redacted non-allowlisted values before recording. Native `X-Language` is corroborated by the original locale getter/interceptor; no private header value is included here. The complete official `Accept-Language` value was `zh-CN,zh;q=0.9;q=0.9,en-US;q=0.8;q=0.8,en;q=0.7;q=0.7`.

`refreshHeaders` is used only for the exact AuthService URL. Work gateway requests retain upstream's `kimi-code-cli/0.36.0` and daimon 0.6.10 device headers. www.kimi.com requests retain upstream's 3.2.20 desktop-menu metadata; the separate www User-Agent discussion remains #363.

## Shared refresh lineage: both directions

All times are **2026-10-24 UTC**. The two consumers begin with the same pair from the new temporary login. The plugin uses the actual production `auth.refresh`/`auth.usage` hooks in an isolated harness; the desktop uses its original AuthService and TokenStore. This run does not exercise Magpie's credential-file commit path.

| Time | Operation and observation |
| --- | --- |
| 15:14:47 | The official native RPC returns the shared starting pair. Desktop access expires at 15:29:47. |
| 15:21:07–08 | Plugin rotates that pair; both tokens change and monthly stats return 200. Only this initial round forces the hook's expiry metadata to start promptly. The desktop still holds the original pair. |
| 15:29:53–54 | After the desktop access expires naturally, its original `TokenStore.ensureValidToken()` uses the retained old refresh and receives 200/new access/new refresh. This is over eight minutes after the plugin's rotation, rather than an immediate replay. |
| 15:30:06 | The native desktop's renewed access reads membership stats with 200; the Work key in its own temporary daemon file reads `/models` with 200. |
| 15:36:50 | The plugin's previously retained access expired naturally at 15:36:07. Calling `auth.refresh` with its unmodified stored expiry rotates its own retained refresh successfully (200), then monthly stats return 200. No desktop re-import occurs; the desktop pair remains unchanged and fresh. The temporary browser has already been closed. |
| 15:37:30 | Native membership stats and the temporary desktop's Work `/models` still return 200. |

This session therefore did **not** show single-use rotation that immediately invalidates the other consumer. Both retained branches renewed successfully over the observed interval. It does not establish an unlimited reuse/grace period, future revocation behavior or months of coexistence. If either saved branch is later rejected, the provider shows the explicit reconnect state; it does not silently switch accounts or rewrite the desktop's credentials.

## Account storage and reconnect

Only explicit sign-in imports the desktop membership pair. `auth.refresh` returns replacements for the host's conditional commit; usage never writes or rotates. Magpie checks the expected access/refresh pair under its auth-store lock, so a late completion cannot restore logout or overwrite another login. Pending exchanges/cached rotations are keyed by exact credentials, including independent reconnects for the same account. The plugin creates no token file and never writes Kimi's configuration. Magpie's account-scoped credential file is private plaintext with atomic flushed writes and mode `0600`, not an encrypted vault.

All official reference-only accounts through 0.1.10 require an explicit reconnect once after this upgrade. The error includes `sign-in has expired`, which Magpie's quota card recognizes as the localized signed-out/re-add-account state; its detail gives `magpie plugin login kimi-work`. No hidden migration consumes desktop credentials. Paired accounts from earlier PR builds retain their format. A rejected refresh requires reconnecting; network/429/5xx failures retain the stored login. Desktop sign-in alone does not update an already saved Magpie pair.

## Regression validation

On Bun 1.4.3 with disposable HOME/XDG directories: **76 plugin tests passed**, 0 failed, 316 assertions; the focused hook check and all **25** plugin hook checks passed. Full-repository test results and the exact final commit are recorded in PR #218's CI evidence. An initial restricted-sandbox run could not bind test loopback ports or reach the public model catalog; the same tests passed with those facilities available, without changing any other package. Tests use synthetic credentials and preserve the real-profile guards.

The independent code review found no new P1/P2. It separately reran the 76 focused tests and confirmed that upstream's model/header/menu helpers are retained, exact-pair concurrency and host conditional-save ownership remain intact, and the English reconnect marker reaches Magpie's localized signed-out card. This does not claim a new live persistence-failure or OpenCode renewal test. Streaming-body cancellation retains its original abort reason and sends no request after cancellation.

## Limits

The monthly meter reports `subscriptionBalance.amountUsedRatio`; Code's share is text from `subscriptionBalance.kimiCodeUsedRatio`, never a second allowance. Expiration fields are not asserted to be reset times. Inference continues to read the local desktop Work key and enforce its exact gateway origin/account binding. Membership renewal does not replace a revoked Work key.

This upgrade's live test is renewal and read-only membership/model access, not a new inference or a desktop UI conversation. Previous macOS and Windows streaming checks are historical coverage. Windows refresh, Linux, Intel macOS, long sleep/offline intervals, months of continuous renewal and future server revocation policy remain unverified. Automatic renewal does not guarantee a permanent session.
