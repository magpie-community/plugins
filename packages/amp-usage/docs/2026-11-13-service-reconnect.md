# Amp Usage 运行中断连问题记录

记录日期：2026-11-13。

状态：已定位并修复一条可复现的旧页面断连路径（改为固定令牌）；已在本地分支 `amp-usage/service-reconnect` 提交为 0.1.2，未推送或发布。采集锁交接改为有界后台重试。故障电脑上的完整因果链尚未验证。

## 结论

最可能的原因是：其他插件自动更新触发 Magpie 共享插件宿主重启，Amp Usage 服务重新生成访问令牌，但已打开的页面仍使用旧令牌。服务返回的鉴权失败响应缺少 CORS 头，沙箱页面无法读取其中的重连提示，因此显示“本地服务没有响应，请重新打开页面”，并持续使用失效令牌。

该路径已有源码和本地请求验证支持，且与故障电脑的日志、浏览器访问正常及重新打开后恢复的现象一致。但尚未取得故障窗口当时的请求状态码，不能把本次实际故障完全归因于令牌失效。

日志还记录过 Amp Usage 因采集锁被占用而加载失败。这是另一个需要处理的服务生命周期问题，当前补丁尚未覆盖。

## 环境与现象

- 故障发生在另一台 Windows / amd64 电脑，不是当前开发电脑。
- 提供的日志最新启动记录为 Magpie `0.1.3962`，时间为 2026-11-13 09:33:19。日志开头的 `0.1.2665` 是较早历史记录。
- 日志曾出现从本地目录加载 Amp Usage；故障时该目录的具体提交和插件版本未确认。
- Magpie 内的 Amp Usage 页面使用一段时间后出现“本地服务没有响应，请重新打开页面”。
- 同一台电脑在浏览器新开 `http://127.0.0.1:3497/?lang=zh` 后显示正常。
- 用户随后反馈“重新打开正常了”。此前提供的是退出并重启 Magpie，以及离开页面超过 10 分钟再返回两种方法，未进一步确认实际采用哪种。
- 截图保留“读取于 15:29”和“334 条记录未计入”，说明页面曾成功取得状态。15:29 是扫描时间，不是可确定的断线时间；排除计数与连接错误是不同问题。

检查本地 Magpie 源码发现，`internal/plugin/updates.go` 在成功更新插件后调用 `Restart()`；`internal/plugin/host.go` 会替换共享宿主，旧宿主可能等待在途调用结束后退出。此机制能够解释为什么更新其他插件也会影响 Amp Usage 服务，但未将故障电脑二进制与本地源码逐版本比对。

### 采集锁冲突

11-12 11:24:12，在插件更新及宿主启动记录之后，出现以下错误，位于原始日志 681–683 行：

```text
Error: Another Amp collector is running for this Magpie configuration.
    at acquireLock (.../amp-usage/lib/collector.mjs:54:17)
    at async startServer (.../amp-usage/lib/server.mjs:18:25)
```

修复前，`acquireLock()` 在锁文件中的 PID 仍可探测到时直接拒绝启动。按本地 Magpie 源码（`01eb3ed`，未与故障电脑版本逐行比对），可复现的交接路径是：

1. `Restart()` 立即把后续调用交给新宿主；旧宿主若仍有调用（如流式回复）未完成，会继续运行最多 10 分钟（`retireWait`），期间保持持有采集锁和端口。
2. 新宿主加载插件时只调用一次 `server()`，失败后该宿主生命周期内不再重试。
3. 旧宿主到期被结束后，3497 端口无人监听，直到下一次宿主重启（例如下一小时的插件更新）。

这种情况下页面和浏览器都会失败，与 11-13 浏览器访问正常的现象不同，因此它不是本次截图的直接原因，但符合 11-12 的报错。旧宿主被强制结束时不会执行 `exit` 回调，锁文件残留；PID 已失效时下次启动会接管，若 Windows 恰好复用该 PID 则可能误判为占用，这一低概率情况不在本次修复范围内。

### 其他异常

日志还包含 WebView2 请求处理异常、11-12 更新时磁盘空间不足，以及后续 Go 运行时内存分配路径中的异常堆栈。目前没有证据将这些异常直接关联到本次页面断连。Factory 登录失效也不能直接解释 Amp Usage 的页面请求失败。

## 已验证的代码缺陷

相关实现：[`lib/server.mjs`](../lib/server.mjs)、[`ui/app.js`](../ui/app.js)、[`lib/collector.mjs`](../lib/collector.mjs)。

1. 服务每次启动都会通过 `randomBytes(32)` 生成新令牌，并写入页面 HTML。
2. 页面启动时读取令牌，此后所有 API 请求一直使用该值。
3. 修复前，服务在令牌校验成功后才设置 `Access-Control-Allow-Origin`；令牌失效时提前返回 403 和 `code: "reconnect"`，响应没有 CORS 头。
4. Magpie 插件页面处于不允许同源身份的 iframe 沙箱中，请求可携带 `Origin: null`。缺少 CORS 头的 403 响应无法被页面脚本读取。
5. 页面将请求异常和 JSON 解析异常统一映射为 `unreachable`，显示“本地服务没有响应”，且没有处理令牌失效后的自动重连。

在开发电脑的运行中服务上，以 `Origin: null` 发起只读验证得到：

| 请求使用的令牌 | HTTP 状态 | CORS 响应头 | 结果 |
| --- | --- | --- | --- |
| 当前页面的新令牌 | 200 | `Access-Control-Allow-Origin: null` | 正常返回状态 |
| 模拟旧令牌 | 403 | 缺失 | 返回 `code: "reconnect"`，但沙箱脚本无法读取 |

上述验证证明该响应路径存在缺陷，不代表直接观测到了故障电脑旧页面的请求。

## 当前本地补丁

| 文件 | 修改 | 覆盖的故障 |
| --- | --- | --- |
| [`lib/server.mjs`](../lib/server.mjs) | 令牌首次生成后写入数据目录 `service-token.json`（私有权限），之后每次启动沿用；文件缺失或格式不对时重新生成 | 宿主重启后已打开页面的令牌仍然有效，不需要重新加载页面 |
| 同上 | Host 和 Origin 校验通过后，在令牌校验前设置 API 的 CORS 响应头 | 令牌确实失效时（如令牌文件被删除），沙箱页面能读到 `reconnect` 并显示“请重新打开”，而不是误报“本地服务没有响应” |
| [`index.mjs`](../index.mjs)、[`lib/collector.mjs`](../lib/collector.mjs) | 锁被活着的实例占用（`ELOCKED`）或端口被占用（`EADDRINUSE`）时，`server()` 记录一条日志后立即返回，服务在后台每 5 秒重试，最长 11 分钟；其他启动错误照旧直接失败，配置变化后旧的重试停止 | 覆盖旧宿主最长 10 分钟的退出窗口；不删除活跃锁，不会出现两个采集器同时工作 |
| [`ui/app.js`](../ui/app.js) | 请求设置 10 秒超时，同一时间最多保留一个状态轮询 | 避免请求无限等待和轮询堆积 |
| 同上 | 状态读取恢复后清除连接失败提示，忽略落后于新操作的轮询错误 | 宿主重启期间的短暂不可达在服务恢复后自动消失 |
| [`test/server.test.mjs`](../test/server.test.mjs)、[`test/ui.test.mjs`](../test/ui.test.mjs) | 补充回归用例 | 覆盖重启后旧令牌仍可用、锁占用时后台等待后启动、鉴权失败响应、超时恢复及请求竞态 |

曾考虑在收到 `reconnect` 后由页面自动导航以获取新令牌，最终改为固定令牌：不依赖沙箱 iframe 的重新导航，也没有导航时服务恰好再次重启导致页面停在错误页的竞态。

令牌保存在磁盘上，同一用户的本地进程可以读取；这些进程本来就能直接读取同一目录的采集数据，Host 和 Origin 校验仍然保留。

补丁不处理超过 11 分钟仍未释放的锁（如长期重复实例或 PID 复用），也不解决持续进程崩溃或 WebView 自身异常；超时后记录错误并放弃，待下次宿主调用时重新尝试。

## 临时恢复办法

- 可在故障电脑浏览器中打开 Amp Usage 的本地地址；如修改过端口，应使用配置中的端口。
- 可通过 Windows 托盘菜单退出 Magpie，再启动并打开 Amp Usage。正在通过 Magpie 进行的请求应先结束；仅点击窗口关闭按钮通常只是隐藏窗口。
- 按当前检查的 Magpie 源码，未设置 `keepAlive` 的插件页面在离开超过 10 分钟后会释放，再次进入时重新加载。短暂切换侧栏不会立即重建页面；故障电脑具体版本的行为尚未单独验证。
- 页面右上角的刷新图标只触发数据刷新，不能替代重新加载页面获取新令牌。

这些操作用于恢复使用，不代表根因已经修复。整个应用重启还会改变服务进程和锁的状态，因此“重启后恢复”不能单独区分令牌失效与锁冲突。

## 后续处理与验收

1. **验证宿主重启后页面继续可用**：在 Windows Magpie 中保持页面打开，触发插件更新或宿主重启，确认页面无需重新打开即可恢复状态读取。
2. **验证短暂不可达**：让服务短暂停止后恢复，确认请求数量受控、页面保留已有展示，并在服务恢复后完成连接。
3. **验证采集锁交接**：在 Windows Magpie 中让旧宿主保持一个进行中的调用，同时触发插件更新，确认日志出现一次 `Retrying`，旧宿主退出后 Amp Usage 在 5 秒内恢复监听。
4. **观察长期占用**：若日志出现 `gave up waiting`，说明锁被长期占用或 PID 被复用，需要单独定位，不能直接删除活跃锁。
5. **在故障电脑验证后发布**：记录插件实际版本、宿主重启时间、恢复耗时和失败请求状态；验证其他插件更新后不再需要人工重新打开 Amp Usage。
