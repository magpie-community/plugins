# Changelog

One entry per version, newest first. This lists what a user has to know to upgrade.

## 0.4.0 - 2026-11-19

The engine is AgentCompass v0.7.3 (pinned at `3f949be`, the `v0.7.3` tag), with the reference data of that release (schema 8: a value at every effort a gateway offers, or a declared known gap, the `provider_names` table and the Magpie preset table `host_providers.magpie`). `src/` is the source repository's at `2abc419`. The source repository compares the port with AgentCompass's `allocator.plan` on a committed sample of 2,801 rows drawn from a grid of 112,028 (efforts `default`, `none`, `minimal` and `ultra` included; names under a maker's default, under a provider's declaration, a repository id, decorated and multi-slash spellings, a retired pair and `other_weights` pairs), plus 280 bare-name rows and 1,028 named-model rows (8 pools of several providers, each with one bundle unchecked, undetected, marked unavailable or offering another effort, in both orders: a bare name across accounts, a prefix obeyed, a prefix dropped level by level, a Magpie preset id as a prefix), with `model_resolution.resolve_model` on 980 cases (names on the endpoints that serve them, against the shipped table and a constructed one whose providers disagree), `expand_host_providers` on 12 Magpie list ids, `quota_pools.applicable_windows` on the 3 moved rows, `model_pin_problem` and `task_intake.named_pin` on 121 values (the round-5 review's fuzz corpus of blanks, empty segments, effort suffixes, auto ids and controls, efforts around a byte-order mark, and values that are not text, lists and objects among them) with `plan`'s refusal of each as `constraints.model` and as `constraints.bundle`, a chain's worker under 166 pins of those pools (whether it stays: the pin does not move it, `pin_moved`, and it can run), and 36 pins over two accounts of one provider named by account id, and the user-score overlay with AgentCompass's for five user-score documents (one keyed under `provider_names`) (cells, measured efforts, operating-point floors, derived facets and the candidate note at every effort); every row, case and model is alike.

**Upgrading**

- **Efforts run `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`, `ultra`** (`user-scores.js` `EFFORTS`, AgentCompass's `user_scores.EFFORTS`). A bare name on a provider with no launch table (a gateway) is now offered at every effort the data times, `none`, `minimal` and `ultra` included; give a row `efforts[]` to run it at fewer. A row's own list is still what it runs at.
- **Candidates from your gateway**: `scripts/candidates-from-models.mjs` turns your Magpie's `GET /v1/models` into `candidateModels` rows with Magpie's own efforts per model ([reference](docs/reference.md#candidates-from-the-gateway)). A model Magpie lists with no reasoning levels becomes a row at `default`, its one configuration: one candidate, scored where the data reads `default` (High), and sent to Magpie as the bare model with no effort.
- **Mode B's effort answer** is a point of Magpie's effort scale (`low`, `medium`, `high`, `xhigh`) for every effort: `none` and `minimal` answer `low` (they answered `high`), `max` and `ultra` `xhigh`, `default` what it reads as (High). A route with no effort on that scale gets no effort answer, so Magpie keeps the effort the request asked for (it was told `high`).
- **Fix: an `ultra` route goes to Magpie as `<model>:max`.** Magpie splits only `none` to `max` off a model and sends `ultra` as `max` (`internal/gateway/gateway.go` askedAt, `ir.go` effortOf, v0.1.4603); `<model>:ultra` reached the vendor as a model of that whole name. Found by the sandbox run on Magpie 0.1.4603.
- **Fix: `onRequest` stays inside Magpie's 250 ms on a long session.** On a runtime that never saw the session the plugin decides its earlier turns again from the history (up to 4 back), and each replayed turn ranked the whole pool again, so a request's work grew with its turn: with the converter's rows Magpie logged `onRequest: took too long` from a conversation's fourth turn and passed `agentcompass/auto` on unrouted. A request's work no longer grows with its turn: a replayed decision reuses the ranking of the same input within the request, a pin's hold is judged once per pin, a name is resolved once per catalogue, and the ranking's sort keys are computed once per candidate. Routing is unchanged (the source repository's parity sample and `test/engine-071.test.mjs` pass as before). On Magpie 0.1.4603 with 108 rows, sessions of eight turns took 6 to 140 ms per request in the plugin's hooks ([limits](docs/reference.md#limits-inside-magpie)).
- **The converter leaves Magpie's routing groups out** (`auto/<model>`, `group/<id>`), naming each on stderr: Magpie picks a group's member, so a row you unchecked could serve a request routed to the group. A found group's models are listed as rows of their own, one per preset.
- **Fix: a pin goes out under the name typed** when the pool lists it on the route's preset and the ranking keeps that listing: with `deepseek/deepseek-flash` and `deepseek/deepseek-v4-flash` listing one row, a pin of `deepseek/deepseek-v4-flash` was sent as `deepseek/deepseek-flash`. A listing its own filters leave out (its `when`) is not sent; the route stays the engine's and a warning says why ([pins](docs/reference.md#candidates-pins-and-refusals)). With no pin the ranking still picks among a row's listings.
- **Fix: a bare row of a model that takes no effort is sent with none.** A row the data reads at one operating point (its vendor documents no reasoning control, e.g. `ministral-8b-2512`) and that lists no efforts in the pool (a bare `modelsByProvider` name, a bare `candidateModels` name) went to Magpie as `<model>:none`, and Magpie passed `reasoning_effort: none` to the upstream (it keeps the effort asked for a model that lists no levels). It is now sent bare, with no effort field (`sentEffort` in the decision); the decision and the session keep the engine's effort, so a pinned session on such a row stays held. A row that lists efforts, and an effort a pin names, is sent at the effort routed.
- **A hold rebuilt from the message history says so.** A runtime that did not serve a session's earlier turns decides them again with the current request's pins (an earlier turn's pin is not in the history), so after a pinned turn a later turn without the pin can go elsewhere; such a hold now says `continuation.stateFrom: "history"` with a notice, also in Magpie's log, and names no earlier route, where it said only `held: true` before (since 0.2.2). A hold from the runtime's own record says `stateFrom: "record"`. New exports: `routeDecider`, `holdJudge` (`middleware.js`).
- **`userScores` schema 4.** A table of schema 3 (0.3.0) is read and upgraded: a score under a name v0.7.0 resolved through an alias v0.7.1 removed or re-targeted (`gemini-4-pro`, `gemini-4-ultra`, `claude-opus-5`, `claude-sonnet-5`, `claude-fable-5`, `grok-4`, `kimi-k3.1-pro-highspeed`, `glm-5.3-flash`, `deepseek-flash`, `deepseek-v4-flash`, `deepseek-v4.1-flash`, `mimo-v2.6-pro-ultraspeed`) moves to the row v0.7.0 meant, so it keeps scoring the model you scored. A score whose name resolves to no row is kept in your table and ignored; it no longer makes a row of its own. A hand-written score now fills every effort the panel steps to, and no curve inverts along effort.
- **Model identity moved** (AgentCompass v0.7.1): `gemini-4-pro` and `gemini-4-ultra` are no longer aliases of `gemini-4-argon-high` (they are now family names, with no scores); `claude-opus-5`, `claude-sonnet-5`, `claude-fable-5`, DeepSeek's dated snapshots, `glm-5.3-flash`, `kimi-k3.1-pro-highspeed` and `mimo-v2.6-pro-ultraspeed` are rows of their own; `claude-haiku-4-5-20251001` is an alias of `claude-haiku-4-5`. A `candidateModels` entry or pin under one of these names now reaches that row, or is out of automatic routing with a warning if it has none.
- **`gpt-6-pro`** is `gpt-6-astra` at one operating point above `max`: a maintainer score on it never reads below that point, and a candidate's note shows both inputs and which binds.
- **The candidate note of a manual score** says what routing reads on each facet at the candidate's effort (`manual capability scores applied, read at <effort>: ...`).
- **The catalog warning of a family name** no longer says it is scored as an estimate of its series' row: such a name has no scores, as the code already did since 0.3.0.
- **Removed exports**: `EFFORT_ORDER` (`catalog.js`, `quota-economy.js`; use `EFFORTS` from `user-scores.js`). New: `EFFORTS`, `MEASURED_EFFORTS`, `EDGES`, `edgeAnchor`, `anchorEffort`, `boundAlongEffort`, `operatingPointFloor`, `appliedScores`, `appliedNote`, `DERIVED_FROM_LARGER` (`user-scores.js`); `readingEffort` (`axis-scores.js`); `V0_7_0`, `v070Row` (`released-names.js`); `FIVE_AXIS_EFFORT_READINGS`, `FIVE_AXIS_EFFORT_STEPS` (`reference-data.js`). A task's `include_unverified` and `force_fast` are no longer read (AgentCompass v0.7.1: a caller cannot lift the launch-evidence check; this port carries no fast mode). Provider names (`catalog.js`): new `PROVIDER_NAMES`, `PROVIDER_NAME_STATUSES`, `servingProviders`, `defaultFor`, `makerDefault`, `undecorated`, `servedModel`; `resolveModel` takes the table and the serving endpoints as its fifth and sixth arguments and answers `provider`; `DIRECT_SOURCES` adds `provider` and `default`; `canonicalModel` answers a value that reads the same row again (`<provider>/<model>` for a pair with no row, the name as given for a repository id whose row's own id reads another row) and takes the endpoints as its fifth argument. New in `user-scores.js`: `resolveModelKey`, `scoreLayer`. A host catalogue's table (`catalog.js`): new `providerNamesOf`, `catalogTables`, `NO_PROVIDER_NAMES`, and `resolveListed` (a list id whose model part holds a `/`, read on its preset); `canonicalModel`, `servedModel`, `rowKey`, `modelSpec`, `healthKey` and `catalogNameWarning` take the `provider_names` table as their last argument, `resolveModelKey`, `scoreLayer` and `scoredModels` likewise; `withoutUnconstrainingTag` is exported from `fleet.js`. `options.catalog.providerNames` is read (a catalogue with its own `models` and no table reads none).
- **A model name reads the row its provider serves** ([reference](docs/reference.md#candidates-pins-and-refusals)). The serving provider is the part of a candidate's name before the first `/` (Magpie's own listing id, `<preset>/<model>`, as the converter writes it), or the preset a `modelsByProvider` list is for. A name its maker moved to a newer dated snapshot reads as that snapshot on every provider: `deepseek-v4-pro` as `deepseek-v4-pro-0813`, `deepseek-v4-flash` and `deepseek-v4.1-flash` as `deepseek-v4.1-flash-1017`, while DeepSeek's repository ids (`deepseek-ai/DeepSeek-V4-Pro`, ...) keep their own undated rows. A pair a provider declares with no row (Google's retired `gemini-3.1-flash-lite-preview`, an `other_weights` listing) is its own model, `<provider>/<model>`, with no scores: out of automatic routing with the reason in `warnings`, dispatched when you name it. On the saved Magpie 0.1.4470 catalog this closes the 15 pairs 0.4.0's first draft scored as other weights: the 8 `deepseek-v4-pro` and `deepseek-v4-flash` pairs on `deepseek` read the dated snapshots (covered), the 3 `ministral-*-2512` pairs on `mistral` read their rows by Mistral's declaration (covered), and the 4 `gemini-3.1-flash-lite-preview` pairs on `google` are retired (they routed as `gemini-3.1-flash-lite`; now only when named). 698 of the catalog's 739 gated pairs are covered and routable for every work kind that demands no image input, the other 41 being AgentCompass's declared known gaps.
- **`userScores` keys** read the maker's default, never a provider's declaration: a score under `deepseek-v4-pro` lands on `deepseek-v4-pro-0813`, and the row's own id (`deepseek-v4-pro-0813`) wins over it for a target both name, whatever their order in your table.
- **A named model** ([reference](docs/reference.md#candidates-pins-and-refusals)). A bare name (`gpt-6.1-sol`) names that model on every candidate, whatever spelling or preset it is listed under; the candidates that cannot run (unchecked, unhealthy, marked unavailable, kept out by `when`, without the effort) are out each with its own reason and the best of the rest is routed. A name with a prefix (`openai/gpt-6.1-sol`, `<preset>/<model>`) is obeyed: it names the candidates listed under exactly that spelling and the candidates of that model on the preset or account the prefix names, and when none of them can run the pin is refused, never served by another candidate. This changes 0.3.0's answer for a prefixed name of a model another preset lists bare: write the bare name when any preset will do. A prefix that names no candidate is dropped and the rest read again from the start, so `openai/gpt-6.1-sol` with only a bare `gpt-6.1-sol` listed still reaches it, and `opencode/deepseek-v4-flash` with nothing named `opencode` is the bare `deepseek-v4-flash`. A Magpie preset id is a prefix too: a list id `<preset>/<model>` and each name of a preset's `modelsByProvider` list are offered on that preset. A malformed name (an empty part around `/` or `:`, a bare `:high`, an `auto:` id without its account and harness, a blank or a value that is not text) is refused with `invalid_model_pin` and what is wrong with it; it was refused as not among the candidates. A value that is not text is refused whatever it is, `0`, `false` and `NaN` included (they were read as no pin and routed automatically); only an absent value, `null` or `""` is no pin, and blanks are those Python's `str.strip()` removes. A malformed `pinnedBundle` (or a task's `pinned_bundle`) is refused the same way (it answered `pin_not_in_pool`). A Magpie seat (a quotas key `<provider>/<account>`) is a prefix: `claude/work/<model>` names that seat only, `work/<model>` the seats named `work`, `claude/<model>` every `claude` seat, and the longest leading part that names something and a candidate with the rest is the prefix, then the shorter ones (`claude/work/<model>` named every `claude` seat, and `work/<model>` was dropped as unknown). A seat prefix decides which candidate the plugin picks and refuses; it cannot bind which seat Magpie then uses: the account Magpie hands `onAccount` names no seat (its `name` is the provider's, its `ref` a keyed hash of the login), so no account is skipped for a pin. A session held on a route keeps it only when the request names nothing, or names the held route among the routes the pin names and that route can run (a warm request answers a pin as a cold one does); Mode B holds a turn as `onRequest` and `hooks` do, on the route as the candidates name it and at an effort the pool still offers (it answered and recorded the canonical name, so on a `<preset>/<model>` pool the next turn pinning the held route lost its hold, and it held an effort the pool no longer offered); a malformed pin is refused before any hold, in `onRequest`, `hooks` and Mode B alike (a held session kept its route for a pin of another preset, of a preset that does not offer the model, or a malformed one, and Mode B read the pins only after its hold). In `onProvider` a prefix that names only another preset's row (of `candidateModels`, or now of another preset's `modelsByProvider` list) is left alone: the plugin does not rewrite the body, and Magpie, which lets `onProvider` neither reject nor skip, sends the attempt to the preset it is trying; list the presets in `candidateModels` to have such a pin refused in `onRequest` ([reference](docs/reference.md#candidates-pins-and-refusals)). A pin is still refused when every candidate it names is a row you marked `disabled` (`pin_unavailable`): the plugin has no separate record of the user's own naming, which is what lets AgentCompass launch an unchecked model the user names.
- **Fix: an unchecked effort on one preset no longer turns it off on others.** In 0.3.0 a row `{ "model": "<preset>/<model>", "effort": ..., "disabled": true }` turned that effort off on every row of the model that had no quota account, on every preset (they shared the gateway account). It now applies to the preset it is listed under, presets that serve one catalog (`qwen`, `qwen-cn`, `qwencloud`; `zai`, `zhipu`; `moonshot`, `moonshot-cn`) being separate presets; a bare disabled row still turns the effort off on every row of the account.
- **A Magpie preset reads the models.dev catalog it serves** (`provider_names.host_providers.magpie`: `opencode-zen` serves `opencode`, `tencent-cloud` serves `tencent-tokenhub`, 17 presets), only in the Magpie adapter: the Cindy plugin and a direct caller of the allocator read a preset id as a provider id like any other. On the saved Magpie 0.1.4470 catalog this moves the 3 `opencode-zen/deepseek-v4-flash` pairs, which routed as DeepSeek's `deepseek-v4.1-flash-1017`, to OpenCode's own `deepseek-v4-flash`: other weights with no row, out of automatic routing with the reason in `warnings`, dispatched when you name it. Every table (a provider's declaration, a maker's default, a row, an alias) reads a name in one order, the full id, then what follows each `/`, then the last segment, so a list id with a `/` in its model part reads as the same name listed on its preset.
- **New exports** (since the first draft of 0.4.0): `slashSuffixes`, `expandHostProviders`, `listedPreset`, `magpieOptions`, `MAGPIE_HOST`, `LIST_HOST`, `modelPinProblem` (never throws), `checkModelPin`, `InvalidModelPin`, `pinGiven` (whether a pin value is given: anything but `undefined`, `null` and `""`), `pyStrip` (`catalog.js`; `providerNamesOf` of a catalogue `magpieOptions` marked carries the host, which `resolveListed` and `listedPreset` read); `pinPool`, `pinNamesBundle` (whether a pin names a bundle in a pool, through `pinMatchingBundles`, as AgentCompass's `account_fleet.pin_names_bundle`), `pinMatchesIdentity` (the identity test alone, AgentCompass's `pin_matches_identity`), `pinReading`, `pinMatchingBundles`, `effectivePin`, `pinMatchedIds`, `bundleProviders`, `bundlePresets`, `advertisedModel` (`candidate-eval.js`). `selectBestRoute` answers `error: "invalid_model_pin"` for a malformed name and reads `pinOnlyModels` (rows a named model is matched over that never compete: `onProvider` passes the other presets' rows of `candidateModels` and of their `modelsByProvider` lists; `candidateOffers` takes the same rows as its sixth argument); `pinKeepsHold` (`allocator.js`) is new, and `refusalSummary` passes that code and its sentence on; `normalizeTask` takes the pool (`pinPool`, `fleet`) to read the name as the pool reads it. `resolveModel` answers `bare` (the spelling the row or declaration was reached by); `rowKey` and `rowKeyOf` take the serving endpoints as their last argument; `modelPinMatches`, `exactPin` and `bundleNamed` take the ranking context in place of the model. Every entry of a preset's list in `onProvider` carries `presets` (the preset id as Magpie gives it) and `served` (the catalogs it serves), and one it converts also `launch_model` (the name as the preset lists it); a `candidateModels` row whose name is a list id carries the same two under the Magpie adapter.

## 0.3.0 - 2026-11-18

The engine is AgentCompass v0.7.0 (pinned at `7827cdb`, the `v0.7.0` tag), with the reference data of that release; `src/` is the source repository's at `c27dd73`. The source repository compares the port with AgentCompass's `allocator.plan` on a committed sample of 1,085 rows drawn from a grid of 43,372 (the whole grid was also compared once); every row is alike. This version also carries what 0.2.2 was to bring (prepared on 2026-11-18, never published), the first item below.

**Upgrading**

- **A row's own `efforts[]` is what it runs at** (from 0.2.2). Before, the efforts a row listed were intersected with the launch table shipped with the version (`dispatch_efforts`): a listed effort the table lacked was dropped, and a row whose efforts the table did not list at all was kept but out of automatic routing. Now the list is used as written and the table applies only to rows that list no efforts. An effort the shipped data does not score leaves automatic routing with a data error naming the missing data; naming the model still dispatches it. The `not_dispatchable` flag is gone. If your `candidateModels` list efforts your upstream cannot run, remove them. An empty `efforts: []` counts as no list.
- **The profile changed.** A profile names one of 11 work kinds (`creative_ideation`, `architecture_reasoning`, `code_implementation`, `frontend_ui`, `code_audit`, `exploration_forensics`, `web_research`, `visual_analysis`, `text_processing`, `live_loop`, `gui_control`) with its depth `primary_level` 1..3, an optional `secondary_kind` with `secondary_level`, `access`, `local_only`, `needs_visual`, `wants_fast`, `expected_hours` and `task_count`. `axis_demand` is projected from the kinds and depths through AgentCompass's declared signature table; it may still be given explicitly. `needs_gui`, `read_only_review` and `multi_task` are derived. `reasoning_depth`, `code_complexity`, `interaction_style`, `hours_confidence` and `urgency` are gone, and the first category is `creativity` (was `divergence`). A profile of the 0.2.x shape is refused with `invalid_caller_profile`; nothing reads it for compatibility. A valid one: [reference](docs/reference.md#task-profile).
- **The classifier** is asked AgentCompass's v0.7.0 prompt with its classifier cases (OpenAI-compatible) or its ten questions (`jev`). An answer of the old shape is invalid; the in-memory cache revalidates every entry on read, so nothing old is served.
- **`userScores`**: level 3 is now the panel's best and levels above 3 extrapolate. Write `{ "schema_version": 3, "scores": { ... } }`. A table without `schema_version` is read as the 0.2.x shape and upgraded by AgentCompass's declared steps (`divergence` renamed `creativity`, then the level-3 conversion): your table is converted, never dropped or refused. A hand-written `tool_operation.responsiveness` level bounds the other efforts in the facet's direction.
- **An `aesthetics` demand of 2 or 3** also needs `tool_operation.image_recognition` data; a model without it leaves automatic routing with the missing facet named.
- **An advisor-only model** (`gpt-6-pro`) is also kept out of a task with `access: "write"`.
- **A pool row's `when.max_reasoning_depth` is now `when.max_primary_level`.** An old key is ignored.
- **Removed exports**: `INTERACTION_STYLES` (`catalog.js`); `FIVE_AXIS_DEMAND_LEVELS`, `FIVE_AXIS_DEMAND_SCHEMA` (`axis-scores.js`); `SCORER_SYSTEM_PROMPT`, `JEV_SCORE_QUESTIONS`, `JEV_STYLE_CRITERIA`, `JEV_EFFORT_BANDS`, `JEV_URGENCY_CRITERIA`, `JEV_NOUL_QUESTIONS` (`scorer-live.js`); `PROFILE_FLAGS`, `MULTI_TASK_QUESTION`, `READ_ONLY_REVIEW_QUESTION` (`profiler-core.js`). New: `WORK_KINDS`, `WORK_KIND_SIGNATURES`, `ROLE_FN`, `projectAxisDemand` and the question texts (`profiler-core.js`); `SCORER_PROMPT`, `scorerSchema`, `scorerEvidence`, `profileQuestions`, `PROFILE_*` (`scorer-live.js`); `LEVEL_FACETS`, `FACET_CATEGORY` (`axis-scores.js`); `upgradeScores`, `LOCAL_UPGRADES`, `convertLevel` (`user-scores.js`); `CLASSIFIER_CASES`, `LEVEL3_CONVERSIONS` (`reference-data.js`). `taskKind` and `profileKind` take no policy.
- The reference data is AgentCompass v0.7.0's, including the GPT-6.2 rows. Nothing is fetched at run time.

## 0.2.1 - 2026-11-13

The engine follows AgentCompass `2844342` (v0.6.0 plus one routing rule).

- **A `needs_visual` task requires image input at every `tool_operation` level.** Before, the image-input gate applied only at `tool_operation` 3, so a task marked `needs_visual` (or `needs_gui`) with a lower level could be routed to a model whose public data says it takes no image input. Such a model now leaves the task, and a model with no cited modality leaves automatic routing; naming it still dispatches it with the data error. Nothing to change when upgrading.

## 0.2.0 - 2026-11-13

The engine is AgentCompass v0.6.0 (pinned at `974eb49`, the `v0.6.0` tag), ported module by module: four capability categories (`divergence`, `coding`, `aesthetics`, `tool_operation`) in place of the 6D/7D vectors and the 3D model profile, data gates, and the quota economy. The source repository compares the port with AgentCompass's `allocator.plan` on a committed sample of 1,451 rows, drawn from a grid of 58,016. How the engine scores is AgentCompass's ([technical reference](https://github.com/akiiwa-games/AgentCompass/blob/v0.6.0/docs/technical-reference.md#1-how-scoring--allocation-work)).

**Upgrading**

- **The profile changed.** `axis_demand`, `access`, `wants_fast` and `read_only_review` are required; `context_scale`, `hallucination_risk`, `error_cost`, the top-level `divergence` and `realtime_loop` are gone. A profile of the old shape is refused with `invalid_caller_profile`; nothing reads it for compatibility. A valid one: [reference](docs/reference.md#task-profile).
- **`realtime_loop` is removed** (the option, the request field and the `realtime_loop` session hold).
- **A family or unknown name has no scores.** `claude-opus-9` is no longer scored as a generic row or as an estimate of its family: automatic routing does not pick it, and naming it dispatches it with a data-error warning.
- **An account with no `plan` has unknown capacity** and is out of automatic routing: put `plan` in `quotas`.
- **No ability floor, over-qualification penalty or realtime step-down.** The fit and the quota economy choose the effort.
- **New option `userScores`**: your own category scores for a model, ahead of the maintainers' and measured ones.
- **Removed exports**: from `catalog.js`, `DEFAULT_MODELS`, `DEFAULT_SCORING_POLICY`, `KIND_TRAITS`, `CANONICAL_ROUTES`, `EFFORT_CURVES` and `resolveModelSpec`; from `index.js`, `computeWindowCost`, `demandForecast`, `evaluateModelQuota`, `CANONICAL_ROUTES` and `healthOnlyQuotas`; from `continuity.js`, `effectiveRealtimeLoop`. `ROUTES` is new. `canonicalModel` returns a family or unknown name as it is.
- **Held sessions**: the difficulty-driven raise on `capability_outgrown` is gone; a request that needs images or a GUI outgrows a model that takes no images.
- **Bare names in a pool**: when a provider has a table of efforts and the model is not in it, the row has no efforts, so a step-down never lands on an unverified effort; `antigravity` and `gemini` no longer borrow another provider's table.
- **A quotas file broken for over 6 hours** excludes only `pool/quotas` in `selectBestRoute`; `onAccount` still answers 503 when every candidate account is unavailable.

Not ported, because Magpie only routes: launching workers, harness order, and the launch side of fast mode.

The comparison with AgentCompass's `allocator.plan` and the Linux sandbox run stay in the source repository, [akiiwa-games/magpie-agentcompass-router](https://github.com/akiiwa-games/magpie-agentcompass-router); this package's tests run on their own. The sandbox script was rewritten for this engine and ran on real Magpie 0.1.4026 (2026-11-13) with real Codex and Claude sign-ins: scenarios 1–10 and 12–15 passed, scenario 13 against both real upstreams included (no `profile` on the wire, the routes the engine gives, a real classifier, one valid account among invalid peers, every account unavailable). The record is `docs/linux-sandbox-e2e-report-0.1.4026.json` there.

## 0.1.6 - 2026-11-08

- **Automatic routing needs a classifier or a caller's profile.** The plugin stopped guessing a profile from regular expressions, word lists or message length. Mode A cannot reach a classifier, so a request to `agentcompass` or `agentcompass/*` without `body.profile` is no longer routed (Magpie's log says `未路由：分类不可用`; a JSON reply carries `agentcompass: { routed: false, notice, reason }`). To keep routing: use Mode B with a scorer, send `body.profile` on every request, or set `defaultModel` for a fixed fallback. `scorerType: "heuristic"` and `prefer_local_heuristic` are gone and count as no classifier. See [Without a profile](docs/reference.md#without-a-profile).
- **Account states, plan-sized capacity and refusal codes.** States `ready`, `plan_inactive`, `usage_failing`, `auth_failed`, `disabled`; a `usage_failing` account keeps dispatching for 6 hours after its last good reading. A configured quotas file that cannot be read is reported as `pool/quotas`. When nothing can serve a request the plugin answers HTTP 503 with a code (`no_route`, `accounts_unavailable`, `pin_not_in_pool`, `model_unhealthy`, `pin_unavailable`, `invalid_caller_profile`) instead of picking an excluded candidate. See [Quotas and accounts](docs/reference.md#quotas-and-accounts) and [refusals](docs/reference.md#candidates-pins-and-refusals).
- **`/v1/systemone` answers only the route** unless `decisionProviderDetails: true`; accounts, quotas, the profile and `warnings` go to the local log, and a refused pin is always `pin_unavailable`.
- **Disabling an effort**: a row with `disabled: true` next to the bare name or `efforts[]` row turns off that effort for the model (and the account, when the row names one).
- **Health and pins**: a failure of a family name no longer takes down the flagship, and naming a model matches only that model's rows.
- **Session holds**: `affinityMode` accepts `cache`, `turn`, `session`, `strict` and `off`; a held effort that the pool no longer offers steps down or ends the hold (`effort_gone`); a session held 24 hours expires.
- **Old model aliases are gone.** Names Magpie once aliased to the then-current flagships (`gpt-5.4`, `claude-3-5-sonnet`, ...) are no longer in the catalog: each logs `candidate name <name> is not in the catalog` once per runtime and is out of automatic routing. Use the names in AgentCompass's [`model-capabilities.md`](https://github.com/akiiwa-games/AgentCompass/blob/v0.6.0/skills/agent-compass/references/model-capabilities.md).
